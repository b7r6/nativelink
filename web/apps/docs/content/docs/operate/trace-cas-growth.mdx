**Who this is for:** your CAS backend grows faster than your builds explain,
and you need to know whether the build is producing new bytes or the same
bytes are being written again. **What you'll have at the end:** output bytes
broken down by producer and by invocation, the reason each producer's output
changes, and the share of backend writes that rewrite a blob already stored.
**Time:** an afternoon of collection that covers repeated builds, then minutes
per analysis.

<Prerequisites>
  A NativeLink build that emits provenance events (release builds up to and
  including v1.7.7 do not), workers and CAS servers whose environment you can
  set and whose stdout you can collect, and Python 3.10 or newer where you run
  the analyzer. [Observability](/operate/observability) covers the logging
  variables this page changes.
</Prerequisites>

## When to use this [#when-to-use-this]

Use it when the backend's capacity curve and the build's output disagree: a
storage account that gains terabytes a day while the bytes your builds produce
for the first time are a small part of that. Two explanations fit, and the fix
for one does nothing for the other.

- **The build produces new content.** Action identities change from run to run
  (stamping, an environment variable whose value changes, a configuration
  flag), or the same action produces different bytes (a nondeterministic tool,
  or inputs that were not materialized the same way twice). Every new digest is
  a new blob.
- **NativeLink writes the same content again.** The Azure store writes without
  a precondition, so uploading a digest it already holds overwrites the blob,
  and a `fast_slow` store writes its slow tier on every accepted upload. With
  blob versioning or soft delete on, the account keeps every overwritten copy,
  so capacity grows with bytes written rather than with bytes that are new.

<SourceLink file="nativelink-store/src/fast_slow_store.rs" symbol="FastSlowStore" />

The provenance events record, for every output, which action and path produced
it and what happened when it was uploaded, and for every write, which digest or
key it was. The analyzer turns them into byte totals that say which of the two
you have.

## Turn the events on [#turn-the-events-on]

Set two environment variables on every worker and every CAS server process,
then restart them:

```sh
export RUST_LOG=info,nativelink_provenance=debug
export NL_LOG=json
```

In a Kubernetes manifest the same two go under `env:` on the worker and CAS
containers:

```yaml
env:
  - name: RUST_LOG
    value: "info,nativelink_provenance=debug"
  - name: NL_LOG
    value: "json"
```

If `RUST_LOG` already has directives, append `,nativelink_provenance=debug`
rather than replacing them. Every event is at `DEBUG` on its own target, so the
rest of the log stays at the level you had. `NL_LOG=json` makes stdout one JSON
object per line, which is what the analyzer reads; with the default `pretty`
format the events are written but the tool cannot parse them.

| Process | Events it emits | Reports that need them |
| --- | --- | --- |
| Worker | `attempt_started`, `output_observed`, `output_upload`, `attempt_finished` | 1 to 4, 6, 7 |
| CAS server (ByteStream, `BatchUpdateBlobs`, `FindMissingBlobs`) | `cas_write`, `find_missing` | 5, and the FindMissingBlobs line of 6 |
| Any process whose store graph holds the Azure Blob store | `backend_write` | 5 |

Every field of every event is in the
[provenance events reference](/reference/provenance-events).

<Callout type="warn" title="RUST_LOG also drives the OTLP exporters">
  The same filter applies to stdout and to the OTLP log, trace and metric
  layers. With `NL_OTEL_ENDPOINT` or `OTEL_EXPORTER_OTLP_ENDPOINT` set, the
  provenance events also reach your collector as log records, so the volume
  below lands there as well as on stdout. See
  [Observability](/operate/observability#the-configuration).
</Callout>

### Scope and volume [#scope-and-volume]

Start with one worker pool and the CAS servers it talks to, not the whole
fleet. Keep the events on long enough to cover several builds of the same
targets: churn and novelty compare one invocation with the next, so a single
build gives them nothing to compare. A window holding a few CI runs of your
main branch is a good first sample.

Each event is one line of roughly 0.5 to 1 KiB, more with long output paths.

| Event | Emitted once per | Lines |
| --- | --- | --- |
| `attempt_started`, `attempt_finished` | execution attempt | 2 per attempt |
| `output_observed` | output: each file, each file inside an output directory, each symlink, stdout, stderr, and each output directory's index object | 1 per output |
| `output_upload` | distinct digest per attempt | at most 1 per output |
| `cas_write` | blob written through ByteStream or `BatchUpdateBlobs` | per blob, on the server |
| `backend_write` | Azure write | per write, in the process holding the store |
| `find_missing` | `FindMissingBlobs` request | per request, on the server |

A pool that executes 100,000 actions a day with 20 outputs each writes about
4 million lines, around 3 GiB, a day from its workers. Cache hits execute
nothing, so they add no worker events. The analyzer holds about 0.7 GB of
memory per million events; if that is too much, analyze a few hours at a time.

## Collect the logs [#collect-the-logs]

Collect stdout from every worker and every CAS server for the same window.
Filtering to the provenance target and compressing as you go keeps the files
small, and the analyzer reads gzip directly:

```sh
for pod in $(kubectl get pods -l '<worker or CAS selector>' -o name); do
  kubectl logs "$pod" --since=6h \
    | grep -F '"target":"nativelink_provenance"' \
    | gzip > "${pod#pod/}.log.gz"
done
```

Run it once per selector that covers your workers and your CAS servers. If your
log pipeline exports flattened OTLP records instead, export those: the analyzer
also reads JSON objects with `event` and `schema` at the top level. Text before
the first `{` on a line, such as the timestamp `kubectl logs --timestamps`
adds, is ignored.

Events are put in order by timestamp, so hosts need synchronized clocks. A
second of NTP skew is harmless when invocations are minutes apart.

### Seed with a blob inventory [#seed-with-a-blob-inventory]

Without a seed, "new" means new within the window: a digest written yesterday
and written again today counts as a first write. To fix that, pass the digests
the container held when the window started. Any file with a digest per line
works, and so does a CSV whose first column is the blob name, such as an
[Azure blob inventory](https://learn.microsoft.com/azure/storage/blobs/blob-inventory)
report: the analyzer takes the first comma-separated field, drops everything
up to the last `/`, and reads `<hash>-<size>` or a bare hash. A header line is
reported as one line that is not a digest.

## Run the analyzer [#run-the-analyzer]

The analyzer is one Python file with no dependencies, at
`tools/provenance/analyze_provenance.py` in the repository:

```sh
python3 tools/provenance/analyze_provenance.py \
  --seed-digests inventory.csv \
  *.log.gz > report.txt

python3 tools/provenance/analyze_provenance.py --json \
  --seed-digests inventory.csv \
  *.log.gz > report.json
```

Pass every file from the window in one run, because first-observed bytes and
rewrites are deduplicated across all of them. With no files, or `-`, it reads
stdin.

| Option | What it decides |
| --- | --- |
| `--seed-digests FILE` | Digests that existed before the window. They never count as new, and the first in-window write of one is reported as a pre-window rewrite. |
| `--top N` | Rows per ranked table; default 20, and `0` prints all. The per-invocation table is chronological and never cut. |
| `--json` | One JSON document, one key per report, with raw byte counts: for comparing two windows or loading into a notebook. |
| `--wide` | Prints digests and paths in full instead of shortened. |

The text report opens with the observation window (the first and last event
timestamps) and counts of what was read. Rates such as
`3.2 GiB/day at this rate` extrapolate the window; they describe the pool you
collected, not the fleet.

## Read the reports [#read-the-reports]

Every table is weighted by bytes. The text output prints binary units, and the
JSON has raw byte counts.

### 1. Producers by first-observed bytes [#producers-by-first-observed-bytes]

A producer is a target, a mnemonic and an output path. **First observed** is
the size of a digest the first time any output in the window has it, credited
to that producer once, so content that appears at two paths counts once.
**Observed** counts every output every time. A producer with high observed
bytes and low first-observed bytes keeps producing content the CAS already has;
a producer with high first-observed bytes is where new content comes from.
`actions`, `inputs` and `cmds` count distinct action, input root and command
digests across its attempts, and `uploads` is the spread of upload dispositions
for its digests.

stdout and stderr appear as the paths `<stdout>` and `<stderr>`. An output
directory's index object appears under the directory's own path.

### 2. Exact identity [#exact-identity]

Action digests that produced more than one
[manifest fingerprint](/reference/provenance-events#manifest-fingerprint)
among complete attempts. The action was identical, so its command, inputs and
platform were identical, and the outputs still differed. `differing paths`
names the outputs to compare. A row here means the tool is nondeterministic, or
the worker materialized the inputs differently. The fingerprint leaves out
stdout, stderr and directory index objects, so log noise and modification times
do not count.

### 3. Logical producer churn [#logical-producer-churn]

For each target, mnemonic, configuration and output path, the complete attempts
in time order, compared in consecutive pairs. Each pair falls in one class,
weighted by the size of the later output:

| Class | Action digest | Output |
| --- | --- | --- |
| `declared_change_output_change` | changed | changed |
| `declared_change_output_same` | changed | identical |
| `same_action_output_change` | identical | changed |
| `stable` | identical | identical |

`declared changes by what moved` says which part of a changed action moved:
`command` (arguments or environment), `input_root` (input files), both, or
`other`, meaning the platform, timeout or salt. Attempts that did not finish,
or whose outputs were incomplete, are not compared.

### 4. Novelty per invocation [#novelty-per-invocation]

Invocations in order of their first event, each with the bytes of output
digests that no earlier invocation produced and the seed does not hold. If
builds of unchanged code keep adding new bytes run after run, that is growth
the build itself causes; compare the cumulative column's rate with the
backend's. An output that alternates between two versions adds bytes in its
first two runs and nothing after. Attempts whose client sent no invocation ID
are grouped as `(none)`.

### 5. Rewrite amplification [#rewrite-amplification]

Successful writes from `cas_write` (by digest, split by `source`) and from
`backend_write` (by key, split by store and key prefix), divided three ways:

- **first-write**: the first write of that digest or key in the window, and not
  in the seed;
- **rewrite**: a digest or key already written earlier in the window;
- **pre-window**: the first write in the window of a digest the seed says
  already existed.

Failed writes are counted separately. Rewrite and pre-window bytes are writes
of content the backend already had. The `backend bytes / CAS bytes` line
compares what reached Azure with what the CAS service accepted; with
`fast_slow` over Azure it sits close to 1, meaning every accepted write,
re-uploads included, became an Azure write. Key prefixes separate the CAS from
the AC when they share a container, and rewrites under the AC prefix are
expected, because an action result is rewritten under the same key.

### 6. has() health [#has-health]

Before each upload the worker asks the CAS whether it has the digest. The table
splits those decisions by the answer (`present`, `absent`, `error`), with the
bytes, the dispositions and the latency percentiles of the check. The worker
uploads on `error` as well as on `absent`, so error bytes are uploads of blobs
that may already be stored.

**Uploads of digests already stored earlier in the window** counts uploads of a
digest that was uploaded, or reported present, earlier in the window. After
`absent` it means the check gave a false negative or the blob was deleted.
NativeLink's Azure store never deletes blobs, though an Azure lifecycle rule
can. Check the store's `consider_expired_after_s` first: a non-zero value makes
the store report blobs older than that as absent on purpose, and each upload
that follows is an overwrite.

The FindMissingBlobs line summarizes what clients asked the server directly.

### 7. Coverage [#coverage]

How far to trust the other six.

| Line | Read it as |
| --- | --- |
| `attempt_started` with no `attempt_finished` | Attempts cut by the end of the window, or workers that died mid-action. A handful is normal. |
| `attempt_finished` with no `attempt_started` | Attempts cut by the start of the window. Their outputs have no target or invocation. |
| `outputs_complete=false` | Attempts that failed or did not upload everything. Reports 2 and 3 leave them out. |
| observed manifest entries `!= output_count` | Lines lost between the process and your files. Treat every total as a lower bound, and collect closer to stdout. |
| `output_observed` with no target/mnemonic/invocation | Outputs that cannot be attributed, usually because their `attempt_started` is missing. |
| events with an unknown schema | The emitters are newer than the analyzer. Those events are skipped; update `tools/provenance`. |

## Interpret the differential [#interpret-the-differential]

The reports point at one of four causes. Start from the top of report 1 and
find each large producer in the others.

| What you see | Where | Likely cause | Where to look |
| --- | --- | --- | --- |
| Declared change and output change | Report 3 `declared_change_output_change`; in report 1, distinct action digests close to the attempt count | Stamping (the build time or `volatile-status.txt` reaching the action), an environment variable whose value changes per run, or a configuration flag that differs between runs | `input_root` moving points at stamped inputs, `command` moving at arguments or environment. Fetch two `Command` protos from the CAS and diff them. |
| Declared change, same output | Report 3 `declared_change_output_same` | Avoidable invalidation: the action key changes and the output does not. It costs execution time and cache misses, not storage | The same `command` or `input_root` split; usually an environment variable or an input the action does not need |
| Same action, output changes | Report 3 `same_action_output_change`; report 2 | Nondeterminism: timestamps, file order or random IDs embedded in the output. Less often, inputs materialized differently on two workers | Diff two outputs from report 2's `differing paths`. Archives are the usual suspect |
| Same output, uploaded again | Report 5 rewrite and pre-window bytes; report 6 uploads after `error` or a false `absent`; report 1 producers whose observed bytes are far above their first-observed bytes | Amplification: `has()` errors or false negatives, `consider_expired_after_s`, clients uploading again, or `fast_slow` writing the slow tier on each accepted upload | The has() error strings and latency in report 6; the top rewritten digests in report 5 and the invocation count beside each |

### Check the Azure side [#check-the-azure-side]

Compare report 5's backend first-write rate with the storage account's measured
growth per day, from the `UsedCapacity` metric in Azure Monitor or from two blob
inventories a day apart:

- **Growth close to the first-write bytes:** the backend stores new content
  once. The cause is the build; see the first three rows above.
- **Growth close to all backend bytes, first writes plus rewrites:** the
  account is keeping overwritten copies.

Check whether it is:

```sh
az storage account blob-service-properties show \
  --account-name <account> --resource-group <group> \
  --query '{versioning: isVersioningEnabled, softDelete: deleteRetentionPolicy}'
```

With blob versioning on, every Put Blob and Put Block List creates a new
version and keeps the previous one until a lifecycle rule deletes it. Each
write uploads all of its blocks again, so each kept version is billed at full
size. With soft delete on, an overwritten blob's previous data is kept for the
retention period. NativeLink's Azure store writes without `If-None-Match`, so
every byte of rewrite and pre-window in report 5 is one more kept copy. A CAS
key is the hash of its content, so in a CAS container those copies are
identical to the current version. A blob inventory that includes versions and
deleted blobs shows how much of the account they take up.

<VerifyBlock>

  During a build, `kubectl logs <worker-pod> | grep -c '"target":"nativelink_provenance"'`
  is non-zero and climbing. If it stays at zero, `RUST_LOG` lacks the directive
  or the binary does not have the events.

  `python3 tools/provenance/analyze_provenance.py <worker-pod>.log.gz` prints a
  window whose first and last timestamps match your collection, and an
  `Events:` line whose `attempt_started` and `attempt_finished` counts are
  within a few of each other.

  Report 7 shows no events with an unknown schema and no manifest count
  mismatches.

  With CAS server logs in the input, report 5 lists `cas_write` sources; with
  the logs of the process that holds the Azure store, it lists `azure_blob`
  under backend writes.

</VerifyBlock>

## Privacy [#privacy]

The events contain no file contents. They do contain output paths, target
labels, mnemonics, tool invocation and correlation IDs, Bazel action IDs,
configuration IDs, instance names, blob keys and client IP addresses, and so
does the analyzer's output. Handle the logs and the report the way you handle
build logs, and review them before they leave your organization.

## Troubleshooting [#troubleshooting]

| Symptom | Cause | Fix |
| --- | --- | --- |
| `warning: no provenance events found` | `RUST_LOG` lacks `nativelink_provenance=debug`, `NL_LOG` is not `json`, or the binary predates the events | Check the running process's environment, not only the manifest, and restart after changing it |
| Every producer's target is `-` | Worker logs without their `attempt_started` events, or a client that sends no `RequestMetadata` | Collect from the start of the window; check that the client sends the `requestmetadata-bin` header, as Bazel does |
| Report 5's `cas_write` rows show 0 invocations | The writes came from workers, which send no request metadata with their uploads | Expected. Match the digests against report 1 instead |
| Report 5 is empty | No logs from a CAS server or from the process holding the Azure store | Add those logs, or turn the variables on in those processes |
| Warnings about an unknown schema | The emitters are newer than the analyzer | Use the `tools/provenance` from the same source as the binary |
| The analyzer runs out of memory | About 0.7 GB per million events | Analyze a shorter window, or one pool at a time |
